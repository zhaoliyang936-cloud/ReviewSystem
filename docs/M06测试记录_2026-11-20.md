## 2. 规则版本

集中配置类为 `VersionedRecommendationConfig`，当前 `ruleVersion='v1'`。v1 参数：W/T/E 权重分别为 0.60/0.25/0.15，时间截断窗口 7 天，错误率窗口最近 5 条选中证据，冷却 24 小时，默认题数 10，复习/诊断默认槽位 8/2，复习初始知识点数 3，全新用户最多覆盖 5 个知识点，复习池门槛 n>=3。修改任一参数必须同步提升规则版本号。

固定算例：`final_score=30`，所以 `W=1-30/100=0.7`；`d=3.5` 天，所以 `T=min(3.5/7,1)=0.5`；最近 5 条选中证据中 2 错，所以 `E=2/5=0.4`。因此：

`P = 0.60×0.7 + 0.25×0.5 + 0.15×0.4 = 0.42 + 0.125 + 0.06 = 0.605`。

计算使用 `BigDecimal`，上述中间项不四舍五入。

## 4. 构造器注入缺陷与修复

首次执行环境因 Windows socket 10013（Permission denied）无法访问 `127.0.0.1:55434`，当时只完成 `mvn -DskipTests package`，未跑测试，记录如实标注为阻塞。

恢复端口访问后运行全量测试，暴露出一个**会让整个后端启动失败**的缺陷：

```
Failed to instantiate [RecommendationService]: No default constructor found
Caused by: java.lang.NoSuchMethodException: RecommendationService.<init>()
```

`RecommendationService` 同时存在 `(JdbcTemplate, VersionedRecommendationConfig)` 与包私有的 `(JdbcTemplate, VersionedRecommendationConfig, Clock)` 两个构造器，Spring 无法自动判定注入目标，`recommendationService` Bean 创建失败，导致所有 `@SpringBootTest` 上下文启动失败——M04 的 12 条、M05 的 7 条全部连带报错。`mvn -DskipTests package` 不启动上下文，因此打包成功掩盖了该问题；若直接 `mvn spring-boot:run`，应用同样无法启动。

修复方式：为供容器注入的双参构造器标注 `@Autowired`，三参构造器继续供测试传入固定 `Clock`。修复后 73 项全部通过。

### 6.1 阻塞原因不是权限，是数据库没在运行

先澄清端口：本机集群配置里没有 `port`，`postmaster.opts` 记录的启动命令也不带 `-p`，因此不带参数启动时落在默认 **5432**。历史联调是用 `-o "-p 55434"` 启动的，两者指向同一个数据目录 `.m04-audit-syntax-pg`，数据完全一致。

`pg_ctl status` 报 `no server running`，且数据目录残留 `postmaster.pid`（状态 `starting`、端口 5432）与陈旧 pid。删除该 pid 文件后启动：

```bash

```

日志显示 `database system was interrupted; last known up at 2026-11-20 20:38:35`，随后 `automatic recovery in progress` → `redo done` → `database system is ready to accept connections`。启动后 psql 立即可连：

Codex 看到的 `Permission denied (0x0000271D/10013)` 与同时观察到的 socket 10013 一致：当日志显示服务在 20:38 之后已中断（`database system was interrupted`），端口上确实没有监听；叠加执行端沙箱对本地连接的拦截，才表现为 10013 而非 connection refused。

### 6.2 真实库验证暴露的超量缺陷

首次在真实库上只读运行 `RecommendationService.recommend(1,10)`（探针测试，运行后删除，未提交）：

```text
PROBE_RULE=v1 updating=false
PROBE_SIZE review=8 diagnostic=13 items=21
PROBE_SHORTFALL=[]
```

请求 10 条却返回 **21 条**，且 `shortfall` 为空——超量被静默吞掉。

根因：`pick()` 按轮次从 `active` 知识点各取一题，`round()` 内部遍历完整个 `active` 列表才返回，而名额检查 `while(out.size()<slots)` 位于轮次之外。诊断池有 13 个知识点时，一轮就取走 13 条，直接越过 `diagnosticTarget=2`。原测试的诊断池只有 5 个知识点、且复习池不足会触发补位，总数恰好仍是 10，因此没有暴露。

同一原因还导致 `plannedKnowledge` 返回全部候选（2+13=15 个），而不是实际参与选题的知识点。

### 6.3 修复

| 文件 | 改动 |
|---|---|
| `RecommendationService.java` | `round()` 增加 `slots` 参数，内层循环开头 `if(out.size()>=slots) break;`；两处调用同步传参 |
| `RecommendationService.java` | `plannedKnowledge` 改为遍历最终 `items` 按 `knowledgeId` 去重生成，保证与真实选题一致；删除不再使用的 `planned()` |
| `RecommendationServiceTest.java` | 新增第 14 项 `diagnosticPoolLargerThanSlotsDoesNotOvershootCount`：复习池 8 题 + 7 个诊断点各 1 题，断言 `items=10`、`review=8`、`diagnostic=2`、`shortfall` 为空、`plannedKnowledge` 条数等于实际涉及知识点数 |
